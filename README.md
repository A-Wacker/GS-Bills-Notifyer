# GS-Bills-Notifyer

An Android app for tracking ongoing payment plans — financed purchases, settlements,
instalment agreements — that notifies **two** people when something falls due, while only
one of them has to install anything.

The phone gets a push notification each morning. A Google Apps Script emails a matching
digest to whoever else needs to know, from a Google Sheet the app keeps mirrored.

## How it fits together

```
   ┌─────────────────────┐                        ┌──────────────────────┐
   │   Android app       │   full snapshot        │   Google Sheet       │
   │                     │   (HTTPS POST)         │                      │
   │  Room = source of   │ ─────────────────────► │  Bills               │
   │  truth              │                        │  Occurrences         │
   │                     │                        │  Settings            │
   │  ┌───────────────┐  │                        └──────────┬───────────┘
   │  │ morning       │  │                                   │
   │  │ notification  │  │                        ┌──────────▼───────────┐
   │  └───────────────┘  │                        │  Apps Script         │
   │  computed locally,  │                        │  daily trigger       │
   │  works offline      │                        │  → morning email     │
   └─────────────────────┘                        └──────────────────────┘
```

Four decisions shape everything else:

**The local database is the source of truth, not the sheet.** The morning notification is
computed entirely on-device, so it never waits on connectivity. Sync is a background side
effect.

**The whole payment schedule is materialized.** A payment plan is finite, so the app expands
each one into *every* dated instalment and writes them all to the sheet. The Apps Script
therefore contains no date arithmetic at all — it compares a `yyyy-MM-dd` string against
today. Two implementations of recurrence maths would drift on end-of-month and leap-year
cases; there is only one, in Kotlin, and it is [thoroughly
tested](android/domain/src/test/kotlin/com/awacker/billsnotifier/domain/schedule/ScheduleGeneratorTest.kt).

It also means the email keeps working indefinitely even if the phone never syncs again —
every future date is already on the sheet. Only paid state goes stale, and the email says so
when it does.

**Transport is an Apps Script web app, not the Sheets API.** No Google Cloud project, no
OAuth consent screen, no signing-fingerprint setup, no sign-in flow. A shared secret gates
the endpoint.

**The phone is the only writer.** The script owns two columns and restores them over each
incoming snapshot; everything else flows one way. There is no conflict resolution because
there are no conflicts.

## Layout

| Path | What it is |
| --- | --- |
| `android/domain/` | Pure Kotlin/JVM. Schedule generation, payoff maths, money, sheet mapping. No Android dependencies, so it is testable anywhere. |
| `android/app/` | The Android app — Room, WorkManager, Compose UI. |
| `appsscript/` | The Google Apps Script: sync endpoint, daily email digest, setup helpers. |
| `docs/SETUP.md` | Setup, verification and troubleshooting. |
| `docs/PLAN.md` | The original design and the reasoning behind it. |

## Building and testing

```bash
cd android    && ./gradlew :domain:test          # 105 tests — schedule maths, payoff, mapping
cd appsscript && npm test                        # 45 tests — digest selection, sync merge, contract
cd android    && ./gradlew :app:testDebugUnitTest # 25 tests — Room queries, digest notification
cd android    && ./gradlew :app:assembleDebug
```

The first two need no Android SDK. `:app` is only included in the Gradle build when one is
present, so the domain tests run anywhere — but note that where an SDK *is* present, `:app`
is configured even for a `:domain:test` run, so a broken app build script will fail it.

The `:app` tests run under Robolectric, so the Room SQL and the notification path execute for
real on the JVM without an emulator. They cover the digest query (a join and a correlated
subquery that would compile fine while being wrong), the flattening of the domain's sealed
types into columns, and the worker itself — including that a run always arms the next one,
which is the entire mechanism behind a daily notification.

[CI](.github/workflows/ci.yml) runs all of it on every push and uploads a debug APK.

Two of those suites check each other rather than themselves:

- **Schema contract** — a Kotlin test parses `appsscript/Common.gs` and fails if the column
  definitions drift apart. Renaming a column otherwise produces no error anywhere: the sheet
  still fills in, the sync still returns ok, and the email quietly stops finding anything due.
- **Payload contract** — a fixture generated by the Kotlin side is run through the real Apps
  Script functions by the node suite, asserting the digest picks the right rows, skips paid
  ones, totals correctly, and stays idempotent across a sync round trip.

To build the app itself, see [docs/SETUP.md](docs/SETUP.md).

## A note on which notification to trust

The email is the more reliable of the two. It runs on Google's infrastructure; the on-device
notification is at the mercy of whatever the phone's manufacturer does to background work,
and is scheduled inexactly because exact alarms on Android 12+ need a permission restricted
to alarm and calendar apps. Put your own address on the recipient list alongside anyone
else's.
